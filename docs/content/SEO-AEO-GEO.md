# Website writing for SEO, AEO and GEO

Updated: 2026-09-10. Read with [Brand Voice](BRAND-VOICE.md) for website content.
This is an editorial guide, not a completed search audit or implementation.

## What we are optimising for

- **SEO — search engine optimisation:** help relevant people find the website
  through search.
- **AEO — answer engine optimisation:** make useful answers easy to find and
  understand in search and answer tools.
- **GEO — generative engine optimisation:** make content clear and trustworthy
  enough for AI systems to use as a source.

AEO and GEO are working industry terms, not separate technical standards.
Write one useful page for people. Do not create a second version for machines.
No writing pattern can guarantee rankings, snippets, AI mentions, or citations.

Google says its normal SEO foundations apply to AI Overviews and AI Mode;
no special AI files or schema are required. Eligible supporting pages must be
indexed and allowed to show snippets. This is Google-specific guidance, not a
promise about every answer engine. [Source: Google AI features](https://developers.google.com/search/docs/appearance/ai-features)

## Plan before writing

Create a short working brief, scaled to the task:

- Page purpose and intended audience or business moment.
- Main question or search need the page should answer.
- Primary topic and a few related questions, in the intended language.
- Approved facts, useful first-hand evidence, and missing inputs.
- Existing related pages and the intended next action.

For a small edit, check these points without producing a separate document.
Read the relevant page spec rather than the whole planning folder. Confirm
services and routes against the project. The content model is a planning
reference, not proof that every listed offer is live.

Treat candidate topics such as “brand strategy agency Bangkok” or “when to
rebrand a business” as hypotheses, not researched keywords. Do not invent
search volumes, competition scores, or audience demand. Use real query data
when available; request a separate research task if substantial research is needed.

## Write a clear, useful page

The following are Designally editorial choices, not guaranteed ranking factors:

1. Use a clear main heading that identifies the page's subject. A creative
   headline can work if nearby text explains the service and audience.
2. Answer the main question early. Usually a few clear sentences are enough;
   do not impose a fixed word count.
3. Organise supporting detail under descriptive headings. Use question
   headings where readers would naturally ask that question.
4. Explain terms, options, limitations, and the next decision. Use lists or
   tables when they genuinely make information easier to compare.
5. Make key passages understandable on their own: name the service or topic
   instead of relying on vague references such as “this solution.”
6. Add original, approved examples and project evidence where useful. Cite
   external factual claims near the relevant text using reliable sources.
7. Finish with a relevant next step. Do not insert sales messages into every answer.

Use service and location terms naturally. Bangkok is part of Designally's
positioning; it does not justify invented offices or unsupported service areas.
Do not repeat locations mechanically or create near-identical city pages.
Avoid keyword stuffing, hidden text, and bulk pages with little added value.
[Source: Google spam policies](https://developers.google.com/search/docs/essentials/spam-policies)

## Content by page type

| Page | Questions it should help answer |
| --- | --- |
| Home | Who is this for? What does Designally do? Where should I go next? |
| Service | When is this useful? What does it include? How are decisions made? What evidence supports the offer? |
| Project | What was the situation? What did Designally do and why? What was delivered? Which outcomes are verified? |
| Insight | What is the answer? What supports it? When does it apply, and what are its limits? |
| About / Contact | Who is the business? What facts establish credibility? How can someone make contact? |

Add FAQs only for useful questions that the page has not already answered
clearly. Do not add an FAQ block to every page or promise enhanced search
results from FAQ markup. Check current official feature documentation before
proposing structured data.

## Titles, descriptions, links and media

- Write a distinct page title and description that accurately summarise its
  actual content. Include the main topic naturally and the location if relevant.
  Treat preview lengths as editorial aids, not fixed ranking rules.
- Use descriptive link text to relevant existing pages. Follow trailing-slash
  rules. Check the redirect plan before proposing URL changes.
- Describe meaningful images for accessibility. Include project context only
  when verified; do not use alt text as a keyword list. Decorative images should
  follow the component's accessible empty-alt treatment.
- Keep essential explanations as readable HTML text, including important
  information otherwise shown only in artwork or video.
- Use real authors and accurate dates when appropriate. Do not invent expert
  reviewers or change dates just to make an old article look new.
- For planned English and Thai equivalents, preserve facts while adapting
  natural phrasing. Do not create duplicate translations or language metadata
  without checking the actual route plan.

## Technical handoff when implementation is requested

Check that approved public pages can be crawled, that internal links expose
them, and that indexing and snippet controls match their intended status.
Keep placeholders under `noindex`. Any structured data must match visible,
verified content. [Source: Google AI features](https://developers.google.com/search/docs/appearance/ai-features)

Follow repository rules for canonical URLs, metadata, redirects, and framework
documentation. Check existing implementation before adding anything. Do not
automatically add schema, `llms.txt`, packages, crawler permissions, analytics,
or services through a writing task. Search access and AI training access can
have different controls; verify the relevant provider's current documentation
before changing either. Do not assume one bot setting controls both.

## Review and measurement

Before handoff, check that the page answers its intended question, keeps the
brand voice, supports material claims, uses real links, and has accurate
metadata. Note missing evidence and technical work separately. Run only the
repository verification tier required for the files changed.

If measurement is later requested and access exists, compare relevant queries,
search visits, and qualified enquiries against a dated baseline. Record the
tool, date, query, and cited URL when checking AI answers; one result is not
proof of stable visibility. Google includes AI feature traffic within overall
Search Console Web reporting, so do not label all of it as isolated GEO
performance. [Source: Google AI features](https://developers.google.com/search/docs/appearance/ai-features)

Recheck current official guidance before changing technical search behaviour.
This guide does not authorise installing measurement tools or changing the site.
