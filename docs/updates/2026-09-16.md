# 16 September 2026

## The space under the showreel breadcrumb

Reported as looking wrong, with a recollection that 100px had been asked for
"under it only". Both halves turned out to be true, and neither was the problem.

`pb-25` is real, compiles (`.pb-25{padding-bottom:calc(var(--spacing) * 25)}`),
and is 100px — but it is `pb-25 sm:pb-0`, so it applies **below `sm` only**. It
was introduced deliberately in `f526412` and paid for in `--showreel-reserve`;
the 7 September update records dropping it at `sm` as worth 72px of rectangle
height across six viewports. Nothing about it was accidental or stray.

### The gap on desktop was never padding

The hero is `flex min-h-svh items-center`, so the space around the block is
whatever the reserve does not spend, split evenly by `items-center`:

```
free = reserve − pt-20 − pb − mt-6 − caption
     = 288 − 80 − 0 − 24 − ~160  =  ~24px   →  ~12px above, ~12px below
```

So the block sat about **12px** above the fold while carrying **80px** of
`pt-20` above it. Not a wrong measurement — an unbalanced one. That asymmetry is
what read as messy.

### The knob is the reserve, not the padding

`sm:[--showreel-reserve:18rem]` → **`20rem`**. Free space goes 24px → ~56px, so
roughly 28px lands at each end instead of 12px.

Padding cannot do this job. A bottom padding is subtracted from the reserve
*and* then centred against, so it costs the rectangle twice and lands on one
side only. The reserve costs it once and is divided evenly by construction.

**Price: 32px of rectangle height** — 612 → 580 at 1440x900. The alternative
considered was restoring the literal 100px at every size, which would have cost
100px of video and re-spent what the September pass reclaimed.

Mobile is untouched: 22.5rem still carries `pb-25`'s 100px, and its worst case
is 4px of room to spare.

## A grep trap worth knowing: Tailwind scans markdown

Verifying the change, `--showreel-reserve:18rem` still appeared **once** in the
live stylesheet — the one the built page links — while the generated HTML used
only `20rem` and `22.5rem`. The two disagreed.

Neither was wrong. The only occurrence in source is the single `className` in
`showreel.tsx`, which is correct. The `18rem` came from `docs/updates/`, where
the class string is quoted in prose: **Tailwind v4's content detection reads
markdown, so naming a utility in documentation emits a real rule for it.**

Harmless — it is a dead rule nothing references — but two consequences are
worth carrying forward:

1. Documentation can add weight to the production stylesheet, and mentioning a
   class in a historical record keeps it alive in the CSS forever.
2. **Grepping compiled CSS to prove an old value is gone will find the docs
   that mention it.** Enumerating the values in the generated HTML is the
   trustworthy check, because it lists what the page actually uses rather than
   what the stylesheet happens to contain.

## The hero was one viewport unit shorter than the screen

Reported from a phone with a screenshot: a large empty band under the
breadcrumb, with the NEXT section's text ("STRATEGY-LED BRANDING & DESIGN")
glowing through behind Safari's floating toolbar on first paint.

Two separate things were stacked, and only one was the padding.

**The ~100px of orange is `pb-25`** — asked for, accounted for, working.

**The next section showing is a unit mismatch.** The screenshot measures the
rectangle at ~344 CSS px, and the box is `100svh − 360px`, which puts `svh` at
about 704 on that device. The hero section was `min-h-svh`, so it ended at 704
— but iOS 26's floating toolbar OVERLAYS content, so the visible area is the
large viewport, about 794. The ~90px difference at the foot of the screen was
never hero at all. It was the section below.

### The same fault the gradient already had

`page.tsx` had diagnosed this exactly, one layer up:

> `svh` is the small height, so it is short whenever Safari's toolbar is
> collapsed — that was the original band … `lvh` is the maximum, so the box is
> always at least the visible area and cannot fall short under any toolbar
> state.

The gradient stage moved to `h-lvh` on that reasoning. **The hero section and
the showreel box were left on `svh`**, so the identical fault reappeared
underneath it — a cream band there, the following section here.

### The change

- hero section: `min-h-svh` → `min-h-lvh`
- showreel box: `calc(100svh − var(--showreel-reserve))` → `100lvh`

**They must move together.** Raising only the section would turn the extra
~90px into free space, which `items-center` splits — making the gap under the
breadcrumb bigger rather than closing it.

**Not `dvh`**, which looks like the precise answer and is a trap here: it tracks
the visible viewport, so the rectangle would resize every time Safari animates
its toolbar, re-laying the pixel grid mid-scroll — the machinery
`use-showreel-grid.ts` exists to hold still. `lvh` is a fixed number and never
fires it.

**The cost**, accepted knowingly and already accepted once for the stage: with
the toolbar expanded the hero is taller than the visible area, so the foot of
the breadcrumb can sit just below the fold. A hero occasionally a little too
tall beats one reliably too short.

`lg:min-h-svh` on the desktop scroll track and `min-h-svh` on the later section
are deliberately untouched: neither is a first screen, and the latter paints its
own background, so neither can reveal the page behind it.

# Mobile and motion pass

A run of device-reported faults, most of them on a phone. Each one is recorded
with what it actually turned out to be, because in three cases the reported
symptom and the cause were in different files.

## The sofa illustration blanked on its first swap

`sofa-frames.tsx` keeps both frames mounted specifically so the swap has
nothing to load — its own comment says so. It still blanked for a moment.

**Mounting is necessary and not sufficient.** `next/image` defaults to
`loading="lazy"`, and the waiting frame carries `hidden` (`display: none`). A
hidden element has no box, so it never approaches the viewport, so the lazy
heuristic never fires. Frame two — the larger file at 40KB against 25KB — was
not fetched until the swap revealed it.

Both frames now carry `loading="eager"`. Per the installed Next 16 docs that is
the recommended tool here: `priority` is **deprecated in 16**, and `preload`
inserts a `<link>` in the `<head>` for the LCP element, which would put a
below-fold decoration in front of the hero's own resources — `page.tsx` already
records that this page's hint ordering is delicate.

On both frames rather than only the hidden one, because which frame is hidden
follows `lit`'s initial state and pinning it to frame two would move the bug the
first time that default changed.

## The pixel wipe looked finished halfway

Reported as the cover appearing solid at mid-screen. Widening the trigger range
did not help, and the reason is that the trigger range was never the lever.

The layer is `absolute` inside its section, so it scrolls with the page at 1:1
**while** the wave travels up through it. The speeds add:

```
front = boundary − (wave fraction × layer height)
      = (1.2 − 0.95p)·vh − p·vh  =  1.2 − 1.95p
```

The leading edge climbs at roughly twice scroll speed and left the top of the
viewport at **p ≈ 0.62**, with the boundary 62% down. Everything visible was
covered, so it read as solid, and the last 38% of the range animated above the
fold. Measured against the previous window it was slightly worse, not better:
the old range put the exit at 69% down, the wider one at 62%.

**The fix is the wave's travel distance, which is the layer's height.** At
50svh the expression is `1.2 − 1.45p`, so the edge survives to p ≈ 0.83 with the
boundary 41% down — visible for about 69% of the range instead of half of it.
`DEFAULT_LIFT` moves with the height in the same edit: the lift is what puts the
layer's bottom on the boundary, and that invariant is the real rule behind the
old note that "at half a screen it covered the heading".

### 30svh was tried first and produced ellipses

Worth recording, because it is a trap with a clean explanation. The grid is
measured from the layer and `pixelGrid` clamps at 32 columns. A 30svh band has
an aspect near 5.9, and no arrangement inside that clamp fits the cell budget —
so the search falls through to its fallback formula, which tiles the box but
does not keep cells square:

| layer | grid | cell | ratio |
|---|---|---|---|
| 30svh | 32x9 fallback | 60x36 | **1.67** |
| 50svh | 32x9 | 60x60 | 1.00 |
| 100svh | 23x13 | 83x83 | 1.00 |

The dots are drawn with `rounded-full`, so a 1.67 cell renders a flat oval.
**Shortening the band further brings them back** unless the density comes down
with it so the search stays inside its clamp.

### Circles were too small on a phone

The same count that suits a monitor put 288 cells across a 390px screen, about
24px each, which reads as grain. `COMPACT_DENSITY = 120` below a 480px layer
width — chosen from the measured width, like the grid itself, and the same
pattern the showreel uses for `PIXEL_TARGET_CELLS_COMPACT`. A phone now resolves
near 10x11 with cells around 39px.

## The statement lines were cut at the foot of the hero

Two bugs in sequence, the second of them mine.

The lines are placed from the bottom — the first at `bottom-[20%]`, the third at
`bottom-[-8%]` — with type to 20rem, and the hero root clips with
`overflow-hidden`. A `mask-image` on the statement block fades them instead.
It belongs on that block and never on the root, which also carries
`intro-gradient`: masking there would fade the hero's background with it.

**Then the third line still cut, because `mask-repeat` defaults to `repeat`.**
That line hangs outside the element's box on purpose, and a repeating mask tiles
the gradient down there starting opaque again — so the overflow was painted at
full strength and chopped by the clip. The first two lines sit inside the box,
faded correctly, and hid the fault. `no-repeat` makes everything past the box
transparent.

The fade then started at 88%, which was still too tight: that line's glyph
*tops* land at about 88%, so the whole letterform sat inside the last twelfth
and collapsed at once. It starts at 80% now.

## Scroll inertia

Lenis `lerp` 0.1 → **0.075** (the default is confirmed in the installed 1.3.26
constructor). Lower means the page takes longer to catch up, which is what reads
as weight.

Two things it does NOT do, both recorded so nobody expects them:

- **It does not touch the phone.** `syncTouch` defaults to `false`, so touch
  scrolling is left to the platform's own momentum.
- **It does not slow any animation down.** Everything scroll-driven here is
  scrubbed to scroll POSITION, so distance-to-progress is unchanged. To make one
  animation pass more slowly, widen its own scroll range.

## The footer's scribble read as a glitch

Reported as the loop completing, blinking out and redrawing. That was the design:
drawn by 40%, held to 65%, faded to `opacity: 0` by 100%, repeat. Reasonable for
something glimpsed once, wrong in a footer that stays on screen.

One pass with `forwards`, so it draws and holds.

**Known limit:** a CSS animation starts when the element renders, not when it is
seen. The footer is far below the fold, so the draw has almost always finished
before anyone scrolls to it. Drawing on arrival needs an `IntersectionObserver`,
which would make `site-footer.tsx` a Client Component — it is deliberately not
one.

## "What we build": the picture now comes before the words on a phone

Below `lg` a service row is plain flow, so the order was number, text, media.
The row becomes a flex column there with an explicit order, putting the
illustration ahead of the description.

The variants are `max-lg:` rather than plain classes neutralised at `lg`, and
that is deliberate: at `lg` the parts are placed by explicit column lines on one
row, and a stray `order` would run the auto-placement cursor past the text's own
columns and drop it onto a second row.

## The cards animated before they were reached

On a phone the situation cards stack, but a single `ScrollTrigger` on the grid
at `top 85%` drove one timeline with a 0.18s stagger across all three. It fired
when the GRID arrived, so cards two and three played while far below the fold
and were finished by the time they were reached.

**The shape of the arrival now follows the shape of the layout.** Stacked, each
card gets its own trigger and no stagger; side by side, the original single
timeline and its stagger, which is the whole effect when all three are visible
at once.

The per-card trigger is the card's `<article>`, **never the flipper**. The
flipper waits at `translateY(180px)` and ScrollTrigger measures the element it is
given, so using it would offset every start by that much.

The breakpoint is read once on mount. A window dragged across 64rem keeps the
arrangement it was built with until remount; a phone cannot cross it by rotating.

### The insight cards had no reveal at all

So this is new rather than repaired. `insight-card.tsx` is an async Server
Component — it awaits its mask source — so it can neither carry `"use client"`
nor run an effect. `reveal-on-view.tsx` is a small client wrapper that takes the
server-rendered card as children.

It follows the same fail-safe the situation cards use: **the finished state is
what the server sends.** The start state is written before paint and removed on
cleanup, so no JavaScript, a failed hydration and reduced motion all leave the
cards visible and in place. Hiding in CSS and revealing in JS fails the other
way, which is the way that loses content.

The movement — a 1.5rem rise and a fade over 600ms — is newly invented rather
than an existing site idiom, and is the most likely part of this pass to want
changing.

**It is `data-appear`, and it started as `data-reveal`, which is already taken.**
`masked-text.tsx` sets `dataset.reveal` to `hidden` or `in` and styles its lines
with `group-data-[reveal=...]`. The values never collided, so nothing broke on
screen — but a bare `[data-reveal]` rule was attaching a transition to every
MaskedText root on the site. It was caught during verification by reading the
emitted stylesheet and finding FOUR rules for an attribute this pass had only
just introduced. Probing for the rule that was expected would have found it and
stopped; enumerating what was actually there did not.
