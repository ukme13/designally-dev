# 16 September 2026

## The space under the showreel breadcrumb

Reported as looking wrong, with a recollection that 100px had been asked for
"under it only". Both halves turned out to be true, and neither was the problem.

`pb-25` is real, compiles (`.pb-25{padding-bottom:calc(var(--spacing) * 25)}`),
and is 100px — but it is `pb-25 sm:pb-0`, so it applies **below `sm` only**. It
was introduced deliberately in `f526412` and paid for in `--showreel-reserve`;
the 7 September update records dropping it at `sm` as worth 72px of rectangle
height across six viewports. Nothing about it was accidental or stray.

### The gap on desktop was never padding

The hero is `flex min-h-svh items-center`, so the space around the block is
whatever the reserve does not spend, split evenly by `items-center`:

```
free = reserve − pt-20 − pb − mt-6 − caption
     = 288 − 80 − 0 − 24 − ~160  =  ~24px   →  ~12px above, ~12px below
```

So the block sat about **12px** above the fold while carrying **80px** of
`pt-20` above it. Not a wrong measurement — an unbalanced one. That asymmetry is
what read as messy.

### The knob is the reserve, not the padding

`sm:[--showreel-reserve:18rem]` → **`20rem`**. Free space goes 24px → ~56px, so
roughly 28px lands at each end instead of 12px.

Padding cannot do this job. A bottom padding is subtracted from the reserve
*and* then centred against, so it costs the rectangle twice and lands on one
side only. The reserve costs it once and is divided evenly by construction.

**Price: 32px of rectangle height** — 612 → 580 at 1440x900. The alternative
considered was restoring the literal 100px at every size, which would have cost
100px of video and re-spent what the September pass reclaimed.

Mobile is untouched: 22.5rem still carries `pb-25`'s 100px, and its worst case
is 4px of room to spare.

## A grep trap worth knowing: Tailwind scans markdown

Verifying the change, `--showreel-reserve:18rem` still appeared **once** in the
live stylesheet — the one the built page links — while the generated HTML used
only `20rem` and `22.5rem`. The two disagreed.

Neither was wrong. The only occurrence in source is the single `className` in
`showreel.tsx`, which is correct. The `18rem` came from `docs/updates/`, where
the class string is quoted in prose: **Tailwind v4's content detection reads
markdown, so naming a utility in documentation emits a real rule for it.**

Harmless — it is a dead rule nothing references — but two consequences are
worth carrying forward:

1. Documentation can add weight to the production stylesheet, and mentioning a
   class in a historical record keeps it alive in the CSS forever.
2. **Grepping compiled CSS to prove an old value is gone will find the docs
   that mention it.** Enumerating the values in the generated HTML is the
   trustworthy check, because it lists what the page actually uses rather than
   what the stylesheet happens to contain.

## The hero was one viewport unit shorter than the screen

Reported from a phone with a screenshot: a large empty band under the
breadcrumb, with the NEXT section's text ("STRATEGY-LED BRANDING & DESIGN")
glowing through behind Safari's floating toolbar on first paint.

Two separate things were stacked, and only one was the padding.

**The ~100px of orange is `pb-25`** — asked for, accounted for, working.

**The next section showing is a unit mismatch.** The screenshot measures the
rectangle at ~344 CSS px, and the box is `100svh − 360px`, which puts `svh` at
about 704 on that device. The hero section was `min-h-svh`, so it ended at 704
— but iOS 26's floating toolbar OVERLAYS content, so the visible area is the
large viewport, about 794. The ~90px difference at the foot of the screen was
never hero at all. It was the section below.

### The same fault the gradient already had

`page.tsx` had diagnosed this exactly, one layer up:

> `svh` is the small height, so it is short whenever Safari's toolbar is
> collapsed — that was the original band … `lvh` is the maximum, so the box is
> always at least the visible area and cannot fall short under any toolbar
> state.

The gradient stage moved to `h-lvh` on that reasoning. **The hero section and
the showreel box were left on `svh`**, so the identical fault reappeared
underneath it — a cream band there, the following section here.

### The change

- hero section: `min-h-svh` → `min-h-lvh`
- showreel box: `calc(100svh − var(--showreel-reserve))` → `100lvh`

**They must move together.** Raising only the section would turn the extra
~90px into free space, which `items-center` splits — making the gap under the
breadcrumb bigger rather than closing it.

**Not `dvh`**, which looks like the precise answer and is a trap here: it tracks
the visible viewport, so the rectangle would resize every time Safari animates
its toolbar, re-laying the pixel grid mid-scroll — the machinery
`use-showreel-grid.ts` exists to hold still. `lvh` is a fixed number and never
fires it.

**The cost**, accepted knowingly and already accepted once for the stage: with
the toolbar expanded the hero is taller than the visible area, so the foot of
the breadcrumb can sit just below the fold. A hero occasionally a little too
tall beats one reliably too short.

`lg:min-h-svh` on the desktop scroll track and `min-h-svh` on the later section
are deliberately untouched: neither is a first screen, and the latter paints its
own background, so neither can reveal the page behind it.
