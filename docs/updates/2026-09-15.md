# Updates — 2026-09-15

Two iPhone-only homepage faults, reported against iOS 26 Safari on an
iPhone 17. **One is fixed and awaiting a device test; the other is unresolved
and no longer being guessed at.** Nothing here has been confirmed on a real
iPhone by the author of this change — see Outstanding.

## 1. Safari's screen-edge colours — RESOLVED, accepted as-is

**Reported:** the areas behind the status bar and the bottom toolbar are solid
bands that do not match the hero. The wanted result was the one
`fridaybangkok.com` appears to get: the page continuing behind Safari's
controls with a soft fade, rather than any solid band.

**That fade does not exist.** The reference site gets the same flat sampled
band this one does — its seam is just invisible. See **What is known** below.
The real mismatch here is confined to the bottom edge at `scrollY = 0`, it
self-corrects on scroll, and it has been accepted rather than papered over.

### What is documented

Safari 26 no longer honours `<meta name="theme-color">` for browser-UI tinting.
It parses the tag and ignores the value, then picks the colour itself by
sampling a `background-color` from a `position: fixed` or `position: sticky`
element near the edge in question, falling back to `<body>`. **It never samples
a `background-image`**, so the hero's `bg-linear-to-b from-surface-base
to-primary-300` cannot contribute a colour at all.

### What was tried, and reverted

Two `aria-hidden` sticky sampling strips were added to the scroll stage, one per
edge, each carrying the gradient's own stop at that end, on the theory that the
bands should at least *match* the hero.

**That was the wrong goal.** The owner wants no band at all. Feeding Safari's
sampler an opaque `background-color` near an edge is precisely the documented
way to *produce* a solid extension bar, so the strips pushed toward the
behaviour being complained about.

They were reverted the same day. `app/page.tsx` is byte-for-byte identical to
its committed state again — it no longer appears in `git status`.

**The revert is not a fix, and must not be recorded as one.** The solid bands
were reported *before* the strips existed, so removing them only returns the
page to the state that already had the fault.

### What is known — the mechanism, and an error of mine

Settled by inspecting the reference site rather than by more inference.

- Safari 26 samples **one flat colour per edge**, and at `scrollY = 0` it takes
  that colour from `<body>`. It never samples a `background-image`, so a
  gradient can contribute nothing.
- `fridaybangkok.com` sets `body{background:#fff}` and sends only
  `<meta name="viewport" content="width=device-width">` — **no**
  `viewport-fit=cover`, **no** `theme-color`, **no** `color-scheme`.
- **There is no fade, and there never was.** That site gets the identical flat
  band this one does. Its band is invisible because a white `body` meets a white
  page. What reads as a soft fade is the absence of a seam.
- This page's `<body>` is `--surface-base`, cream, while the hero gradient runs
  `from-surface-base` to `to-primary-300`. So the one sampled colour matches its
  top exactly and its bottom not at all:

  | edge | sampled | page there | seam |
  |---|---|---|---|
  | top | cream `#faf9f5` | cream | invisible |
  | bottom | cream `#faf9f5` | orange `#f56341` | visible |

- A true fade behind the chrome is **not achievable**: one flat colour per edge
  is the whole of the behaviour. The achievable goal is an invisible seam, which
  is all the reference site has.

**A confounder never accounted for while this was open.** iOS 26 lets the viewer
choose the toolbar layout — Settings → Safari → Tabs → Compact, Bottom or Top —
and how much of the page shows behind the chrome depends on that choice. Any
future report should say which layout the device is set to.

**An error, recorded rather than quietly edited.** An earlier revision of this
section stated the bands appear at "every scroll position" and that this **ruled
out** the published theory of a `scrollY = 0` fallback that composites real
pixels once scrolled. That theory was not ruled out — **it was correct.** Later
device reports were explicit: the bottom bar is cream at load and turns orange
after a short scroll, which is exactly the documented behaviour. A correct
explanation was discarded on the strength of one early, ambiguous report, and
that cost several rounds of investigation.

### The decision

**Accepted as-is on 15 September 2026.** The mismatch exists only at the top of
the page on first paint and corrects itself as soon as the page is scrolled.

A bottom sampling strip — `sticky bottom-0`, `bg-primary-300`, scoped to the
hero stage so it releases with it — would close the seam, and was built once
already before being reverted. It was judged not worth the markup for a
transient. It remains the fix if that judgement changes; it has never been
tested on a device.

### Deliberately not done

- **`viewport-fit=cover` was not added.** Not because it is unavailable —
  see the correction below — but because it lets content run under the notch and
  home indicator while nothing in this layout compensates with
  `env(safe-area-inset-*)`, so the fixed mobile header would slide under the
  status bar.
- **No scroll runway, and no forced initial scroll offset.** Both change how the
  hero first presents itself, which is the thing being preserved.

**Correction.** An earlier draft said `viewportFit` is not a field on Next's
`Viewport` type. That was wrong, and it was wrong because only the `Viewport`
interface body was read, not the `ViewportLayout` base it extends.
`node_modules/next/dist/lib/metadata/types/extra-types.d.ts` declares
`viewportFit?: 'auto' | 'cover' | 'contain'`, and `metadata.js` appends
`viewport-fit=<value>` to the meta tag. It is available; it is simply not set.

### What is still in the tree

**`themeColor` has since been REMOVED** — from both `app/layout.tsx` and
`app/_lib/site.ts`, later the same day. The `viewport` export now carries only
`colorScheme: "light"`.

The owner's hypothesis: declaring a `theme-color` is what makes Safari 26 paint
an opaque bar, and its absence is why `fridaybangkok.com` gets the native
translucent material. That site sends no `theme-color`, no `color-scheme` and
no `viewport-fit` — only `width=device-width`.

**This contradicts the sources cited above**, which say Safari 26 ignores the
tag outright and would make the removal a no-op. Those sources have already
been wrong about this device once — they were used to "rule out" the
`scrollY = 0` fallback, which turned out to be the correct explanation — so the
hypothesis is being settled on hardware rather than by more reading. If the
frosted material appears, the sources are wrong and the absence is
load-bearing.

Known cost, and it is not Safari's: Chrome and Android **do** honour
`theme-color`, so their address bar now falls back to its own default rather
than the page's cream. Accepted for the test, and reversible.

Still different from the reference site, and deliberately so: `colorScheme:
"light"` remains (it is a browser-UI hint in its own right, and the next
candidate if this removal changes nothing), and `width`/`initialScale` stay at
Next's default `width=device-width, initial-scale=1` — dropping
`initial-scale` would change pinch-zoom, an accessibility change with no place
in a chrome-colour test.

**Verification of the removal.** Tier 3, since `app/layout.tsx` is a layout
file:

- `npm run typecheck`, `npm run lint` — clean.
- `npm run build` (Turbopack) and `npm run build -- --webpack` — both passed.
- `<meta name="theme-color">`: **0 occurrences across every generated page**,
  not only the homepage. Checked over all of `.next/server/app/*.html`, because
  the root layout affects every route.
- `<meta name="color-scheme" content="light"/>` still emitted, confirmed on `/`
  and `/about/`.
- Viewport meta reads exactly `width=device-width, initial-scale=1`.
- No code references `themeColor` any more. Three mentions survive in `app/`
  and all three are prose inside comments — the note on the `viewport` export
  and the gravestone in `site.ts`.
- Regression guard on the same build: `url(#` 0, shape wrapper `opacity-100`,
  one `<canvas>` (the hold canvas), `h-lvh` / `mt-[-100lvh]` intact.

**What this does NOT establish.** Only that the tag is gone. Whether its
absence changes what Safari 26 paints is the entire point of the change and is
unverified here — it needs a standard Safari tab on the device.

## 2. The showreel's pixel entrance never drew on iPhone — FIXED

**Reported as** the showreel appearing frozen during the reveal, then playing
normally once it finished.

**What was observed**, from the owner's description: on first load nothing is
visible for the whole entrance and the film appears in one step at the end; on a
project switch the previous frame is held for the entrance and the new film
appears when it finishes. **The pixel reveal was never drawn at all on iOS; it
was not frozen.** The held previous frame during a switch is `holdRef` working
exactly as designed and was never a fault.

This also **disproves the previous review's hypothesis**, which was that Safari
was failing to redraw an animated mask *over* the video.

**What is documented:** MDN's browser-compat-data and caniuse both record that
Safari does not support `mask-image` referencing an SVG mask by `url(#id)`. The
note in `SHOWREEL.md` claiming this had been verified in Safari was written
against a probe route that has since been deleted and could not be re-checked;
it has been corrected.

**The WebKit mechanism is UNCONFIRMED.** The observed behaviour fits the mask
being applied but never re-read as its rects are mutated, and fits equally well
the `url(#id)` reference failing to resolve and being treated as an empty mask,
which hides everything while applied. No WebKit bug report was found for either,
and no device debugging was performed. Earlier wording here asserted the first
of those as fact; that overstated the evidence.

**Fix — the reveal is painted into a `<canvas>`, which depends on no CSS mask
support at all.** The effect is unchanged: same timings, ordering, easing,
geometry and circle-to-square morph.

- `app/_lib/use-showreel-entrance.ts` — rewritten. Per frame: the cells are
  filled as paths, each at its own alpha; `globalCompositeOperation =
  "source-in"` then draws the video frame, which survives only where a cell is
  and at that cell's alpha. Where no cell has arrived the canvas is genuinely
  transparent, so the hero's gradient shows through exactly as the mask
  intended.
  - Cells are **plain JavaScript objects**, not DOM nodes — GSAP tweens their
    numbers and a `requestAnimationFrame` loop paints them, so there is no DOM
    write per pixel per frame.
  - `object-cover` is reproduced in the draw call; backing store capped at 2×
    DPR; the canvas is only resized when the size actually changes, since
    assigning width or height clears it.
  - `roundRect` is feature-detected; without it cells arrive as squares rather
    than resolving from circles.
  - Guarded on `readyState >= 2`, below which the cells would paint as solid
    white blocks.
- `app/_components/showreel.tsx` — the media layer is hidden with `opacity-0`
  for the entrance instead of carrying `mask-image`. **Hidden, not unmounted:**
  the canvas reads frames from that `<video>` with `drawImage`, so it must stay
  laid out, playing and decoding. `hidden` would stop it rendering on iOS.
- `app/_components/showreel-pixels.tsx` — **deleted**; `SHOWREEL_MASK_ID`
  removed from `app/_lib/showreel.ts`. The cell-placement arithmetic moved into
  the hook, which is now its only definition.

Preserved: reduced motion (`mayLoad` false, so no entrance is armed and the
rectangle paints immediately), the project controls, and every failure route.

## 3. The entrance diagnosis was probably WRONG — second pass

After the canvas reveal shipped, the owner reported seeing **no pixel dots at
all** on the iPhone, and supplied a screenshot with Nourigo active.

That screenshot is the evidence that overturns section 2's reasoning:

- The green rectangle in it is **genuine Nourigo footage** — the poster is a
  cream band over a solid green field with fruit characters on the boundary,
  and `object-cover` on a portrait box crops to the vertical middle. The
  characters are visible clipped at the top edge. So the canvas is not painting
  garbage; the film renders correctly.
- **Nourigo was active**, meaning the carousel had already advanced. Every
  advance re-arms the entrance (`setCoverArmed(true); setRevealDone(false)`),
  so the reveal should have been seen several times over. Zero sightings.

**The likely cause is that the entrance never RUNS on iOS**, not that it fails
to paint. `canReveal` is `!revealDone && heroCued && visible && ready &&
playing && !failed`. If `ready` or `playing` never becomes true there, no
timeline is built, nothing is painted, and `PIXEL_COVER_MAX_MS` (~6.9s from the
hero cue) sets `revealDone` and drops the film in whole.

**That reproduces both original observations exactly** — a blank rectangle on
first load, the held outgoing frame on a switch — with the SVG mask playing no
part in either. Section 2's fix was still correct on its own terms: the mask
genuinely does not work on iOS and had to go. But it was probably not the
reported symptom, and this note previously implied it was.

Which of `ready` or `playing` fails **is not known** and cannot be read from a
development machine.

## 4. Breadcrumb: pressing an outer copy sent the strip backwards

**Reported:** pressing the repeated `Laga` at the right-hand end of the strip
scrolled the row left to the first `Laga` instead of staying put.

**Cause, confirmed by reading the code.** `alignToNearestCopy` chose its target
by distance from the strip's centre and was never told which pill had been
pressed. Press the last copy's name and the twin nearest the centre is usually
the MIDDLE copy's own pill, so `nearest === real`, the compensating shift is
skipped entirely, and the centring effect then smooth-scrolls that middle pill
into view — dragging the row leftwards to a different copy of the same name.

**Fix.** The pressed pill wins outright.

- `app/_lib/use-showreel-strip.ts` — `alignToNearestCopy(next, fromCopy?)`.
  When `fromCopy` is given it selects `[data-copy="<fromCopy>"]` directly.
- `app/_components/showreel.tsx` — `selectProject(next, fromCopy?)`, and the
  button passes its own `copy`.
- **Nearest-to-centre is kept as the fallback**, because an automatic advance
  (`crossfadeAt`, the stall timer) has no pressed element and that guess is
  still the right one there.

Pre-existing; not introduced by the canvas work.

## 5. TEMPORARY diagnostic — added, used, REMOVED

A debug panel was added to answer section 3's open question on the device. **It
answered it, and has been removed** — see section 7. What follows is the record
of what it was and why it was built that way.

**It is off unless the URL asks for it: `/?debug=showreel`.** It prints
`mayLoad`, `visible`, `heroCued`, `ready`, `playing`, `failed`, `shouldPlay`,
`canReveal`, `coverArmed`, `revealDone`, `showPixels`, the grid, the current
project, and the element's live `readyState` / `paused` / `currentTime`.

**The live status alone turned out to be uncapturable by hand, and that was a
fault in this panel rather than in anyone's timing.** The reveal lasts 2050ms,
cannot begin before the hero's cue at `INTRO.showreelCue` (1850ms), and
`selectProject` resets the diagnostics on every switch while the carousel
advances on its own — so the completed status survived only a few seconds per
project. Two device captures missed that window: the first landed before the
cue (`heroCued false`, `not started frames=0 ms=0`) and the second after the
entrance had finished (`revealDone true` at `t=2.50`).

So the last row is now **latched and never cleared**:

```
LAST <status> f=<frames> ms=<elapsed> x<completions>
```

Any screenshot after the first reveal now answers the question, whatever the
timing. `painted complete` with a three-figure frame count means the reveal
genuinely ran and drew every frame, so the remaining problem is what it looks
like rather than whether it happens. `drawing timeout` or `media readiness
timeout` with `f=0` means it never drew. `draw failed: …` names the exception.

The count is incremented once per completion, not once per sample, so `x3`
means three reveals have finished — which also proves the entrance re-arms on
project switches.

Statuses are classified by an **in-progress** set (`not started`, `waiting for
media`, `waiting for drawable frame`, `drawing`) rather than a terminal one, so
any new failure string added to the hook is treated as terminal by default.

`useSyncExternalStore`, **not** `useSearchParams` and **not** a state flipped
from an effect:

- `useSearchParams` on a prerendered route forces the client tree up to the
  nearest Suspense boundary to be client-side rendered (installed docs,
  `api-reference/functions/use-search-params`). The homepage is `○ (Static)`.
  That is a structural change for a throwaway flag.
- Setting state in an effect body is what `react-hooks/set-state-in-effect`
  forbids. It was written that way first and **lint refused it** — correctly,
  since this file's own entrance latches are written around that same rule.

The server snapshot returns `false`, so the panel never reaches the static HTML
— verified below.

**To remove:** delete the three module-scope helpers above `Showreel`
(`subscribeDebugFlag`, `readDebugFlag`, `readDebugFlagOnServer`), the `debug` /
`debugVideo` / `debugOutcome` declarations, the sampling effect in full
(including its `inProgress` set and the `completions` / `settled` counters),
and the panel at the end of the returned JSX. All are marked `TEMPORARY
DIAGNOSTIC`.

`revealDiagnostics` and the hook's `diagnosticsRef` parameter are a separate
decision: they are cheap, always-on plumbing rather than debug-only UI, and
`use-showreel-entrance.ts` writes to them unconditionally. Keeping them costs
one ref write per frame; removing them means changing the hook's signature.

## 6. The white band — fixed with `lvh`, after two wrong attempts

**The structural cause, which took three tries to state correctly.** The hero's
background is painted only by `HeroIntro`, which is `absolute inset-0` inside
the sticky box — so the painted area is exactly one viewport unit tall — and
**the stage behind it has no background at all**. `<body>` is cream. So a
sticky box that falls even slightly short of the visible viewport shows a cream
band at the foot of the screen.

That makes the unit the whole question:

| | Behaviour | Result |
|---|---|---|
| `h-svh` | the SMALL height — short whenever the toolbar is collapsed | the original band |
| `h-dvh` | equals the visible viewport at rest, but not mid-transition | band survived |
| `h-lvh` | the LARGE height — the maximum, never shorter | no band |

Now `sticky top-0 h-lvh` with `mt-[-100lvh]` on the content wrapper.

**Correction to an earlier claim in this document.** This section previously
said switching to `h-lvh` was "not a one-line change" because "the stage's
`mt-[-100svh]` pull is coupled to that same height, so switching to `h-lvh`
would shift the layout." **That was wrong.** The pull is *paired* — it is the
same unit as the box, so the two cancel and the stage's height and pin
arithmetic are identical under `svh`, `dvh` or `lvh`. That error is why the
band was left unfixed for a round and why a background-colour workaround was
considered instead.

The cost, and it is real: with the toolbar showing, the gradient's bottom stop
sits just below the fold, so the visible bottom is a touch less orange than the
stop itself. A colour nuance against a cream band.

Painting the stage `bg-primary-300` was the alternative and was **rejected** —
it would add a large opaque background near a viewport edge, which lands back
in the Safari sampling question.

## 7. The reveal was never broken — it was too fine to see

The diagnostic answered section 3's question on the first clean capture:

```
LAST painted complete f=125 ms=2060 x1
```

**The reveal runs and draws 125 frames over 2060ms**, against a designed
`ENTRANCE_MS` of 2050. Every failure theory this document entertained is now
dead, and it is worth listing them so none is revived:

| theory | verdict |
|---|---|
| iOS ignores the SVG mask reference | true, but **not** the reported symptom |
| the gates never satisfy on iOS | disproved — all four read `true` |
| the reveal completes in a single frame | disproved by reading the clock |
| the canvas never draws | disproved — 125 frames |

What was actually wrong is arithmetic. On the reported iPhone the rectangle is
about 337x337, so at 144 cells each cell was 28px and at `PIXEL_CELL_SCALE` 0.9
each dot was 25px — a **3px** gap. The dots touched almost immediately, and
roughly 22 were mid-fade at any instant (`PIXEL_FADE_MS` 200 spread across a
`PIXEL_REVEAL_MS` 1300 scatter). That is a wash, not a grid of pixels.

### The retune

- `PIXEL_CELL_SCALE` 0.9 -> **0.6**.
- `PIXEL_TARGET_CELLS_COMPACT` = **64**, used when the box is narrower than
  `PIXEL_COMPACT_MAX_PX` = **480** CSS px. Desktop keeps 144.
- Selected from the box's measured width inside the existing `ResizeObserver`,
  not from a breakpoint — the same reasoning that made the arrangement dynamic
  in the first place.
- **No timing changed.** `ENTRANCE_MS` is still 2050, so the hero's
  choreography is untouched.

`pixelGrid` was **executed** against these shapes rather than estimated:

| Box | Target | Grid | Cells | Cell | Dot |
|---|---|---|---|---|---|
| 337x337 | 64 | 8x8 | 64 | 42px | 25px |
| 327x427 | 64 | 7x9 | 63 | 47px | 28px |
| 390x520 | 64 | 7x9 | 63 | 56px | 33px |
| 688x387 | 144 | 16x9 | 144 | 43px | 26px |
| 1116x628 | 144 | 16x9 | 144 | 70px | 42px |
| 1400x712 | 144 | 16x8 | 128 | 88px | 53px |

Tablet and up are unchanged. On a phone the dot stays about 25px but its cell
grows from 28px to 42px, so the gap between neighbours goes from 3px to **17px**
— which is the entire difference between grain and pixels.

### The diagnostic is gone

Removed in full: the three module-scope helpers, the `debug` / `debugVideo` /
`debugOutcome` declarations, the sampling effect, and the panel. A grep across
`app/` for `debugOutcome`, `debugVideo`, `subscribeDebugFlag`, `readDebugFlag`,
`useSyncExternalStore` and `debug=showreel` returns nothing.

`revealDiagnostics` and the hook's `diagnosticsRef` parameter were **kept**
deliberately: `use-showreel-entrance.ts` writes to them unconditionally, so
removing them means changing that hook's signature — wider than was asked for.
They cost one ref write per frame and nothing renders them.

### Verification for this pass

Tier 2: one component and one lib file — no routing, no config, no
dependencies, nothing committed.

- `npm run typecheck`, `npm run lint`, `npm run build` (Turbopack) — clean.
- `npm run build -- --webpack` — **skipped**, and named rather than left
  implied. Tier 2 does not call for the second bundler.
- **No compiled-CSS check**: no Tailwind class was added or changed. The usual
  check exists because an unmatched class emits nothing silently; there is no

- Generated HTML — no debug remnants (`mayLoad`, `canReveal`, `LAST ` all **0**);
  `url(#` **0**; shape wrapper `opacity-100`; exactly one `<canvas>`, the hold

## 8. Opaque fixed/sticky surfaces — the hypothesis, and what was actually there

**The hypothesis.** The hero stage is `sticky top-0 h-lvh` with orange
background layers, so Safari sees a sticky element touching the bottom viewport
edge and locks the toolbar to solid orange for the whole page, disabling the
native frosted material. The reported evidence: the bottom bar stays solid
orange even over the pure-white Case Study section.

**The mechanism does not match the markup.** Enumerated from the rendered HTML,
every `fixed`/`sticky` element on the page, before this change:

| element | background |
|---|---|
| mobile header `fixed inset-x-0 top-0` | `bg-transparent` at rest |
| floating header `fixed top-0 left-0` | none, and `hidden` below `md` |
| mobile drawer `fixed inset-0 z-55` | **`bg-surface-base` — opaque cream** |
| skip link | `sr-only`, `focus:fixed` only |
| hero box `sticky top-0 h-lvh` | **none at all** |

**The sticky box is transparent.** Its orange was `HeroIntro`'s
`absolute inset-0 bg-action-primary` — an *absolute grandchild*, which the
documented sampling rules ignore outright. Every orange element in the page was
`absolute` or `relative`. There was **no orange fixed or sticky target to
remove**, so the stated cause could not be the one operating.

There is also a geometric objection: at the Case Study section the stage is two
viewports above the fold, so a released sticky element is not touching any edge.

**What was actually there: the drawer.** `fixed inset-0`, full-viewport, opaque,
closed only by `-translate-y-full` — never unmounted, never `display: none`. It
sits at both edges, on every page, on every phone.

> **Correction, written after section 13.** This paragraph originally ended "it
> is a real violation and it is gone now", meaning the background move had
> settled it. **It had not.** The background was gone from this element for
> several passes afterwards and the drawer still locked Safari's bottom toolbar
> to solid the moment it was opened once. The trigger is the fixed **layer**,
> not its paint — and the fix is `visibility`, not background. See section 13.

### The changes

- **`app/page.tsx` + `app/_components/hero-intro.tsx`** — the solid orange base
  moved out of `HeroIntro` and onto the scroll stage, which is
  `position: relative` and so is not a sampling candidate under any documented
  rule. Independent payoff: the stage is two viewports tall, so once the
  `h-lvh` gradient unpins, what shows beneath is orange rather than `<body>`
  cream. That should close the band still caught on a fast flick.
- **`app/_components/header-shell.tsx`** — the drawer's cream moved from the
  fixed element to its `h-full` inner wrapper. Same pixels, same slide (the
  transform stays on the outer element), but the fixed element is now
  transparent.

**A rejected approach, recorded so it is not retried blindly.** The "correct"
drawer fix is `display: none` when closed while keeping the animation, which
needs `transition-behavior: allow-discrete` and `@starting-style` — in Tailwind
v4 the `transition-discrete` utility and the `starting:` variant. Neither could
be verified against the installed 4.3.3, and an unmatched Tailwind class emits
nothing and no error. The failure mode was therefore a silent no-op **plus** a
broken close animation. Moving the background one level down achieves the same
sampling outcome with no new utilities and no animation risk. The display
toggle remains the escalation if this proves insufficient.

### After

Every `fixed`/`sticky` element now carries **no opaque background**: the mobile
header is transparent, the floating header has none, the drawer has none, the
skip link is `focus:fixed` only, and the hero box has none. Verified by
re-enumerating the rendered HTML, not inferred.

**That was worth doing, but it was not the fix.** Both faults this section was
chasing turned out to have nothing to do with background colour: the toolbar
going solid on scroll was the sticky hero box occupying the toolbar's band
(section 10), and the toolbar locking after the drawer opened was the drawer's
fixed layer surviving its transform (section 13). Removing opaque backgrounds
from edge-adjacent fixed elements is defensible housekeeping; it resolved
neither symptom.

### What this does NOT establish

**Neither change is predicted to fix the orange toolbar**, and that should not
be forgotten if it persists. Nothing in the DOM explains orange over a white
section: there was no orange fixed or sticky element to begin with. The
best-fitting remaining theory is that Safari samples once and does not
re-sample — cream at load from `<body>`, orange after scrolling into the hero,
then orange indefinitely. That has no markup fix.

## 9. The fixed header's scroll background — a cleanup, NOT the cause

> **Correction, written after section 10.** This section originally claimed the
> header was the cause, "found by device testing". It was not, and the owner
> falsified it with a test that had already been run: the header is
> byte-identical shared chrome on `/` and `/about/`, so if its scroll background
> were responsible, `/about/` would break too. It does not — it stays frosted
> through the whole page. The change below is still worth keeping (an opaque
> `fixed` element at a viewport edge is worth not having), but it did not fix
> the reported fault. See section 10.

**The observation that solved it**, from the owner:

- `/about/` — refresh, then scroll the whole page: **true frosted glass
  throughout**. Safari's native compositing works.
- `/` — loads as frosted glass at `scrollY = 0`, then **snaps to solid white
  the instant the page moves**.

That is a state change on scroll, which points at exactly one thing:
`header-shell.tsx` rendered `${atTop ? "bg-transparent" : "bg-surface-base"}`
**on the `fixed inset-x-0 top-0` element itself**. Cream `#faf9f5` is the white
being seen. Scroll once, the fixed bar at the top edge becomes opaque, and
Safari's toolbar tint follows.

`/about/` is not a counter-example: the same switch happens there, but that page
is cream-on-cream, so an opaque cream bar is invisible. Same mechanism, hidden
by luck — the same reason `fridaybangkok.com` looks like it has a "fade" when
it simply has white on white.

### The error in how this was verified

Section 8 enumerated every `fixed`/`sticky` element and concluded none carried
an opaque background. **That enumeration was run against the server-rendered
HTML, which only ever contains the at-rest state.** `atTop` is true at first
paint, so the header always renders `bg-transparent` there and
`bg-surface-base` cannot appear in built markup under any circumstance.

The check was structurally incapable of finding this, and it was still
presented as conclusive. **A rendered-HTML grep cannot verify conditional
styling.** For state-dependent classes the source is the only place to look —
which is what finally found it:

```
grep -rn --include='*.tsx' -E '(fixed|sticky)[^"`]*\$\{[^}]*bg-' app/
```

That now returns nothing.

### The fix

The background moved off the fixed element onto the bar's inner row — the same
pattern already applied to the drawer in section 8. The row is `h-20` and
`w-full`, so on a phone it paints exactly the pixels the header used to, and it
is not positioned, so the sampler ignores it.

Two alternatives were rejected:

- **`bg-transparent` on scroll.** The background is not decorative; it exists so
  the nav stays legible once content scrolls under the fixed bar. Removing it
  leaves dark nav text over arbitrary content.
- **Semi-transparent fill plus `backdrop-blur`.** The sampling research says
  Safari reads `background-color` **and `backdrop-filter`** from fixed elements,
  so a blur may itself be a tint source — trading one unknown for another.

The slide stays on the `<header>` and the colour transition moved with the
background, so the two now sit on different elements and cannot overwrite each
other's `transition-property` — which is what the old combined
`transition-[transform,translate,background-color]` existed to avoid.

## 10. The sticky hero stage — CONFIRMED, and the one fix that worked

**The owner's falsification, and it is sound.** If the `fixed` header's scroll
background were the cause, `/about/` would lose its frosted toolbar on scroll
too — the header is the same component, the same classes, on both routes.
`/about/` stays frosted throughout. The header is ruled out (section 9
corrected accordingly).

**The built output makes this a genuinely controlled experiment**, which is
what four previous rounds lacked:

| route | `fixed` elements | `sticky` elements |
|---|---|---|
| `/` | 4, byte-identical | **1** |
| `/about/`, `/insights/`, `/works/`, `/contact/` | 4, byte-identical | **0** |

One variable. The hypothesis: an *active* sticky element spanning to the bottom
viewport edge is what flips Safari 26's toolbar out of its translucent material
— which also explains the timing, since a sticky box is not yet pinned at
`scrollY = 0` and the toolbar is frosted there.

### The change, and the device result

`sticky top-0 h-lvh` → `sticky top-0 h-[calc(100lvh-6rem)]`, with the paired
offset `mt-[-100lvh]` → `mt-[calc(-100lvh+6rem)]`. The two must always cancel,
or the content stops overlapping the pinned box and the stage shifts.

**CONFIRMED on device.** Holding the sticky box clear of the bottom edge fully
restored Safari 26's native frosted toolbar during scroll on `/`. After five
attempts at this fault, this is the one that worked — and it is the only one
that came from a controlled comparison rather than from reasoning about
documentation. The other four are recorded in sections 1, 8 and 9; all four
were plausible, and all four failed.

**The threshold, measured.** Every value below was tested on an iPhone 17 /
iOS 26:

| inset | result |
|---|---|
| 0px (`h-lvh`) | solid |
| 8px | solid |
| 8px + a `:root` gradient | solid |
| 24px | solid, from `scrollY = 0` |
| **96px (`6rem`)** | **FROSTED** |

So the published ~3px edge-proximity figure does not describe this behaviour at
all. What fits is that Safari's floating bottom toolbar occupies roughly 56-88px
of the viewport, and the trigger is the sticky box extending into the band
*behind* it — not its distance from the edge. The threshold is the toolbar's own
height, which is why 8px and 24px both failed.

**Why the inset is not tuned down.** Walking it up through 40, 56, 72 would have
found the threshold and re-introduced the cropped lettering at the same time:
`HeroIntro` was `absolute inset-0` of this box, so every pixel of inset cropped
the big "Make it…" typography by the same amount. The two constraints move
together and no single number satisfies both. It is solved structurally instead
— see **The structural decoupling** below.

**Visually free, and only because of section 8.** `--action-primary` and the
gradient's `to-primary-300` both resolve to `#f56341`, so the gradient finishes
96px above the fold and meets flat stage orange at a seam that cannot be seen.
Before the orange base moved to the stage, the same change would have leaked
cream `<body>`.

The stage's own height is unchanged (the two values cancel), so only the pin
duration shifts.

**Do not simplify this back to `h-lvh`.** It reads as a redundant `calc` and it
is not. That is the bug.

### The structural decoupling

`HeroIntro` changed from `absolute inset-0` to `absolute inset-x-0 top-0 h-lvh`.
It no longer inherits the shortened box's height: it renders a full viewport
tall and overflows the sticky box's bottom by 96px. The sticky box sets no
overflow rule, so that overflow is visible; `HeroIntro`'s own `overflow-hidden`
still frames the statement lines against a 100lvh box exactly as before any
inset existed.

This rested on Safari sampling the sticky element's **border box** rather than
its painted bounds. **Confirmed on device:** the toolbar keeps its frosted
material and the typography is uncropped, so it is the border box.

Two parse errors were made writing this, both caught by `npm run lint` before
reaching a device, and both recorded in the comment above the element: a JSX
comment placed between `return (` and the element (two sibling expressions where
one is required), and then the rewritten comment quoting JSX comment delimiters
literally, which closed the block comment early and left an unterminated
template literal. Block comments do not nest. Name the delimiters, never spell
them.

### The footer edge, and the overscroll canvas

The bottom overscroll bounced cream while the footer is brand orange. The
overscroll colour comes from the **canvas**, which takes its background from the
root element — and `:root` was a single `--surface-base`, so both ends bounced
cream. Correct at the top, where the hero opens on cream; wrong at the bottom.

`:root` now carries a two-stop gradient, cream to orange. `<body>` has its own
opaque background and spans the whole document, so this is never visible in the
page itself — only past the edges. The 50% split is arbitrary; only the two end
colours are ever read.

**A gradient on the root, deliberately not a fixed strip at the foot of the
page.** After section 10, adding a `fixed` element touching a viewport edge is
precisely how the frosted material is lost — solving an edge-colour problem that
way would trade this fault for the one just fixed. The root element is neither
fixed nor sticky, and Safari never samples a `background-image` for its tint.

### Four false signals from brittle greps — a methodology note

This fault took five rounds, and verification error made it longer. Four
separate greps produced misleading results in one day, and **two of them would
have reported working code as broken**:

| mistake | result |
|---|---|
| Pattern prefix-matched a longer rule | "found" the wrong `transition-*` class |
| `grep -c` on minified CSS | counts *lines*; always 1, meaningless |
| Probed for a pre-normalisation string | `calc(-100lvh + 8px)` returns 0 — Tailwind emits `calc(8px - 100lvh)` |
| Assumed declaration order | `:root{background…` misses it when the minifier puts `background` last, after 27 custom properties |

The rule that would have prevented all four: **dump what was actually emitted
and read it — never test for the string you expect.** And a control helps: if a
known-present rule like `.site-logo` is missing too, the file being grepped is
wrong, not the code.

Related, from section 9: **a rendered-HTML grep cannot verify conditional
styling at all.** Static output only ever contains the at-rest state.

## 11. The `:root` overscroll gradient — SAFE, but it does not work

The bottom overscroll bounced cream while the footer is brand orange. The
overscroll colour comes from the canvas, which takes its background from the
root element, and `:root` carried a single `--surface-base`. A two-stop gradient
was added there, cream to orange, so each end of the document matched what it
adjoins. `<body>` spans the whole document and has its own opaque background, so
the gradient was only ever visible past the edges.

**It was reverted the same day, and the reasoning behind the revert was wrong.**

The frosted toolbar broke again immediately after that pass, and the gradient
looked like the culprit — Safari sampling the root/canvas background to decide
toolbar compositing is a plausible mechanism. It was reverted first as the newer
and more invasive of the two changes shipped together.

**But two changes shipped together, which is the error.** That same pass also
took the sticky inset from 96px down to 8px. Removing the gradient did *not*
restore the frosted material — the next device test was still solid — which
means the gradient was never implicated. The inset was, and section 10 went on
to prove it.

### Retested in isolation — and the answer is two answers

The gradient was re-added later the same day with **nothing else in the pass**,
precisely because the first attempt was unreadable. The device gave a split
result, and the distinction is the whole value of this section:

**It is SAFE.** The frosted toolbar survived scrolling and a drawer open/close
throughout. A root background does **not** influence Safari's toolbar
compositing — the suspicion that it did is now properly disproved rather than
merely unconfirmed, and the two real causes are elsewhere: a sticky element in
the toolbar's band (section 10) and a fixed layer surviving its transform
(section 13).

**It does not work.** The bottom overscroll still bounced cream. `<html>`
carries `h-full`, so **the root element's box is one viewport tall, not the
document.** The canvas rules paint the root's background across the whole canvas
but size and position it to the root's own box, and with `background-repeat` at
its default the gradient **tiles** in viewport-height bands. Which half of a
tile lands at the end of the document depends on that document's height — so the
bounce colour is *arbitrary per route*, not merely wrong. That is worse than a
consistent cream, and why it was reverted a second time rather than kept.

**The proper fix, if it is ever wanted.** The root's box has to span the
document: drop `h-full` from `<html>`, and in the same edit change `<body>`'s
`min-h-full` to `min-h-svh` — a percentage min-height resolves against the
parent's height, so against an auto-height root it collapses and short pages
lose their sticky footer. That touches the root layout and every route, which is
why it was not done on the spot.

**Two routes that cannot work**, recorded so nobody spends time on them:

- An element at the end of the document. The rubber-band area paints the canvas;
  the page never extends into it.
- A `fixed` or `sticky` strip at the foot of the page. That is exactly what
  drops the translucent material (section 10), so it trades one fault for the
  other.

`<body>` cannot carry it either: with no background on the root, a background on
the body *propagates* to the canvas and the body then paints none itself, so it
would show through the page wherever a section has no background of its own.

**Outcome: the cream bounce is accepted, not outstanding.** The durable result
of this test is the safety finding, which closes a question that had been open
across four passes.

## 13. The drawer's fixed layer — CONFIRMED, and the general rule

**The symptom.** Open the mobile menu once, close it, and Safari 26's bottom
toolbar stayed solid white **permanently** — at every scroll position, on every
page, for the rest of the session. Never reproduced without opening the drawer
first.

**Why that timing matters.** The drawer is in the DOM on every page load. If its
mere existence were the trigger, the toolbar would be solid from first paint. It
is not. Something about *painting the open state* promotes the layer, and
closing it by transform never releases it.

**What it was not.** Section 8 had already moved this element's background onto
an inner wrapper, on the theory that Safari samples `background-color` from
fixed elements near an edge. The element carried no background for several
passes afterwards and the fault persisted unchanged. **Paint is not the
trigger.**

### The fix

`visibility: hidden` when closed, `visible` when open, with the flip timed to
land at the end of the slide:

```css
[data-site-drawer] {
  visibility: hidden;
  transition: translate 500ms var(--ease-out) 250ms,
              visibility 0s linear 750ms;
}
[data-site-drawer][data-open] {
  visibility: visible;
  transition: translate 500ms var(--ease-out) 0ms,
              visibility 0s linear 0ms;
}
```

A `0s` change delayed to 750ms is the whole trick: the panel stays rendered for
the entire 500ms sweep (which begins after a 250ms wait for the rows inside to
leave) and is dropped the instant it lands. Opening reverses both to `0ms`, so
it is visible before it starts to move.

**Confirmed on device:** the slide still sweeps smoothly with no snapping, and
the toolbar reliably restores its frosted material once the drawer finishes
closing.

**One rule owns both properties, deliberately.** The element carries no
`transition-*` utility at all. Splitting the slide across a Tailwind utility and
this rule would mean two declarations of `transition-property`, and stylesheet
order — not intent — would decide which survived.

Reduced motion needs its own branch: the global reduced-motion rule collapses
`transition-duration` but leaves delays intact, so without it the panel would
linger visible for 750ms after closing with no animation to justify it.

### The transferable rules

For any project using Safari 26 on iOS, in order of how much time each would
have saved here:

1. **A `fixed` or `sticky` element occupying the bottom toolbar's band makes
   Safari drop its translucent toolbar material.** The band is the toolbar's own
   height — measured at roughly 56-88px, *not* the ~3px edge proximity the
   published sampling research describes. Insets of 0, 8 and 24px all failed;
   96px worked.
2. **A transform does not release a fixed layer.** `-translate-y-full` moves the
   element off screen and WebKit keeps the compositing layer. `visibility:
   hidden` does release it. `display: none` would too, but is harder to animate
   — `visibility` was enough here and keeps the transition trivial.
3. **It is the layer, not the paint.** Removing `background-color` from an
   edge-adjacent fixed element changed nothing in either case. Two separate
   attempts were built on that assumption and both missed.
4. **`theme-color` is irrelevant to this.** Removing it entirely changed
   nothing; it was restored.
5. **The root/canvas background is unproven either way** — see section 11. It
   was reverted as part of a confounded test, never actually disproven.

### How it was found, which is the real lesson

Not by reading. Every documented rule cited across sections 1, 8 and 9 pointed
at `background-color`, and four changes built on those rules all failed.

Both real causes came from **controlled comparisons on the device**: `/` against
`/about/`, identical but for one sticky element (section 10); and the drawer
before and after being opened once, identical but for a promoted layer (this
section). In each case the fix followed immediately from an experiment with one
variable.

  four passes and is now disproved, which is the durable result of that test
  even though the gradient itself was ineffective (section 11).

### Open

- **The bottom overscroll is cream, not the footer's orange — ACCEPTED, not
  open.** The `:root` gradient was retested in isolation and gave a split
  answer: safe for the toolbar, but ineffective, because `<html>`'s `h-full`
  makes the root's box one viewport tall so the background tiles and the bounce
  colour is arbitrary per route (section 11). **Do not simply re-add it.** The
  real fix is to make the root span the document — drop `h-full` from `<html>`
  and change `<body>`'s `min-h-full` to `min-h-svh` in the same edit — which
  touches the root layout and every route, so it was not done on the spot.
- **The navbar reappears when scrolling to the end of the document.**
  `useScrollState` hides the bar only while `y > previous`, and Safari's
  rubber-band bounce at the document end drives `scrollY` back down past the 4px
  `DIRECTION_THRESHOLD`, which reads as an upward scroll. The hook already
  guards this exact hazard at the *top* of the page with the
  `TOP_EXIT`/`TOP_ENTER` hysteresis; `barHidden` has no equivalent at the
  bottom. Same bounce, unhandled at the other end.
- **The `useGradientFade` cream-to-orange fade does not run on mobile.** It
  derives its travel from `stage height − viewport`, and the mobile stage now
  collapses to roughly one viewport, so travel is zero and the hook fails safe
  by leaving the gradient whole. Orange still shows below it because the stage
  paints it. Fixable with an explicit `travelViewports` on mobile.
- `SHOWREEL.md`'s "Verification performed" section still records frame-accurate
  timings measured against the old SVG-mask implementation. The schedule is
  unchanged, but the timings were not re-measured.

### Lessons worth keeping

- **Five attempts, and only the one with a controlled comparison worked.** Four
  were reasoned from documentation — `theme-color` removed (section 1), the
  hero's orange base and the drawer's background moved (section 8), the header's
  scroll background moved (section 9) — and all four missed. The fifth came from
  comparing two routes that differed by exactly one variable (section 10). The
  four failed changes are kept on their own merits, not as fixes.
- **A rendered-HTML grep cannot verify conditional styling.** Static output only
  ever contains the at-rest state; state-dependent classes must be checked in
  the source (section 9).
- **Read what was emitted, never probe for the string you expect.** Four brittle
  greps gave false signals in one day, two of which would have reported working
  code as broken (section 10).
- **Never ship two changes in one pass when testing a hypothesis.** Section 11
  cost a round trip for exactly this.
